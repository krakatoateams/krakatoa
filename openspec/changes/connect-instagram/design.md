## Context

Reference implementations already shipped:
- **YouTube** (`app/api/connections/youtube/{start,callback}/route.ts`, `app/api/connections/youtube/route.ts` DELETE) — Google's stable `refresh_token` grant, `googleapis` SDK.
- **TikTok** (`app/api/connections/tiktok/{start,callback}/route.ts`, `app/api/connections/tiktok/route.ts` DELETE, `lib/tiktok.ts`) — raw `fetch` (no SDK), PKCE-mandatory authorize request, rotating `refresh_token` (invalidated and reissued on every refresh call).
- Both connect flows are independent of the login session ("Model B"), CSRF-protected via an httpOnly `state` cookie compared in the callback, and persist into a single generic `platform_tokens` table: `user_id, platform, access_token, refresh_token, expires_at`, upserted with `onConflict: "user_id,platform"`. This table isn't in `supabase/migrations/` (it predates that convention; lineage in `scripts/migrations/001-remap-users-to-supabase-auth.sql`) and is generic enough for a third `platform` value with no *new column* needed — but `refresh_token` turned out to still carry a `NOT NULL` constraint (an assumption this design got wrong initially; corrected by `056_platform_tokens_nullable_refresh_token.sql` once Instagram's genuinely-null `refresh_token` write hit it in practice — YouTube's own defensive `refresh_token ?? null` had never actually exercised that path, since Google always returns a real one).
- `app/api/connections/status/route.ts` reports which platforms are connected (`{ youtube, tiktok }` today) by querying distinct `platform` values for the user.
- `ConnectionsTab.tsx` renders one interactive row per connected platform (YouTube, TikTok) and one static `StaticConnectionRow status="soon"` stub for Instagram.
- `app/api/cron/route.ts` (the publisher): claims one due post per tick (`MAX_POSTS_PER_RUN = 1`, `maxDuration = 60`) via a conditional update on `publish_started_at` (stale-claim window `CLAIM_STALE_MS = 10 min`), dispatches on `post.platform`, retries transient failures up to `MAX_PUBLISH_ATTEMPTS = 3` (permanent failures — auth/scope/quota — fail immediately via a per-platform `is*PermanentFailure` classifier), and idempotency-gates on a platform-specific ID column (`youtube_video_id`, `tiktok_publish_id`) so a post already published is never re-published.
- The TikTok branch specifically (`tiktok-publish` + `tiktok-photo-post`) established the pattern this proposal leans on hardest: `isPhotoPost` computed from `photo_urls` presence (no separate post-type column), `waitForTikTokPublishOutcome` polling TikTok's status-fetch endpoint **after** Init succeeds (bounded in-request wait: 3s interval, 24s max, comfortably inside the 60s `maxDuration`), persisting the platform's own publish/container ID **immediately** (before the poll) so a mid-poll timeout resumes on the next tick instead of re-calling Init and creating a duplicate post.

**Instagram-specific research (Meta's Instagram Platform docs, current as of this proposal):**
- **OAuth ("Business Login for Instagram"):** authorize at `https://www.instagram.com/oauth/authorize` (`client_id`, `redirect_uri`, `response_type=code`, `scope`, `state`). The authorization code is valid 1 hour, single-use.
- **Code → short-lived token:** `POST https://api.instagram.com/oauth/access_token` (`client_id`, `client_secret`, `code`, `grant_type=authorization_code`, `redirect_uri`) → `{ data: [{ access_token, user_id, permissions }] }`. This token is short-lived (~1 hour).
- **Short-lived → long-lived token:** `GET https://graph.instagram.com/access_token` (`grant_type=ig_exchange_token`, `client_secret`, `access_token`) → `{ access_token, token_type, expires_in }`, valid **60 days**.
- **Refresh a long-lived token:** `GET https://graph.instagram.com/refresh_access_token` (`grant_type=ig_refresh_token`, `access_token`) → same shape, extends another 60 days. Requirements: the token must be **at least 24 hours old**, not yet expired, and carry `instagram_business_basic`. There is **no separate `refresh_token` concept** — the long-lived access token refreshes itself.
- **Content Publishing (the actual publish flow):** `POST /{ig-user-id}/media` (`image_url` + `media_type=IMAGE` for a photo, or `video_url` + `media_type=REELS` for a reel/video; `caption` optional) → `{ id: <container_id> }`. Then `GET /{container_id}?fields=status_code` → one of `IN_PROGRESS`, `FINISHED`, `ERROR`, `EXPIRED` (a container not published within 24h of reaching `FINISHED` expires), or `PUBLISHED` (after the publish call below). Meta recommends polling **once per minute, for up to 5 minutes**. Only once `status_code=FINISHED` can `POST /{ig-user-id}/media_publish` (`creation_id=<container_id>`) succeed, returning the final `{ id: <media_id> }`.
- **Rate limit:** 100 API-published posts per rolling 24h window per Instagram account, checkable via `GET /{ig-user-id}/content_publishing_limit`.
- Sources: [Meta — Publish Content using the Instagram Platform](https://developers.facebook.com/docs/instagram-platform/content-publishing/), [Meta — Business Login for Instagram](https://developers.facebook.com/documentation/instagram-platform/instagram-api-with-instagram-login/business-login). No official Node SDK exists for either the OAuth or the Content Publishing surface — same situation as TikTok, so `lib/instagram.ts` uses raw `fetch`, consistent with `lib/tiktok.ts`'s style.

## Goals / Non-Goals

**Goals:**
- Let a signed-in user authorize Kelolako to publish to their Instagram Business/Creator account via Instagram Business Login, independent of their login session (Model B, matching YouTube/TikTok).
- Persist the long-lived `access_token` + `expires_at` in `platform_tokens` under `platform: "instagram"`.
- Let the user disconnect (delete the stored row).
- Publish a scheduled photo (single image) or video/reel post to the connected account via the cron's existing claim/retry/idempotency contract.
- Build the container-status verification into the *first* publish implementation — not a follow-up fix (see Decisions 3–4, and the direct TikTok-history callout in `proposal.md`).
- Keep the long-lived token alive proactively (Decision 2b) rather than discovering it expired only when a scheduled publish fails.

**Non-Goals:**
- Carousel posts (`media_type=CAROUSEL`, multiple images/videos in one post) — single image or single video/reel only, matching the task's "photo + video/reel" scope.
- Instagram Stories.
- Messaging or comment management (`instagram_business_manage_messages`, `instagram_business_manage_comments`) — not requested scopes; publish-only, same boundary as TikTok/YouTube.
- A generic `connections/[platform]` abstraction — same reasoning as `connect-tiktok` Decision 1.
- Full rate-limit dashboarding — basic error classification only (Decision 8).

## Decisions

### 1. Mirror TikTok/YouTube's Model B shape exactly
Three new routes (`start` / `callback` / `DELETE`) parallel to the existing pairs, rather than a generic `connections/[platform]` dynamic route — same rationale as `connect-tiktok` Decision 1: the three providers' OAuth mechanics differ enough (Instagram's multi-hop token exchange, TikTok's PKCE + rotating refresh, Google's stable refresh_token) that a shared abstraction would need provider-specific branches anyway.

### 2. Token model differs fundamentally from both existing providers — no `refresh_token` grant
Instagram's flow is a **3-hop exchange**, not a 2-hop code-for-tokens like YouTube/TikTok:
1. `code` → short-lived token (1 hour) — `callback` receives this first.
2. Short-lived → long-lived token (60 days) — `callback` performs this exchange **immediately after** step 1, so `platform_tokens` never stores the 1-hour token.
3. (Ongoing) long-lived → refreshed long-lived token (another 60 days) — see Decision 2b, not part of the connect flow itself.

`platform_tokens.refresh_token` is left `NULL` for `platform: "instagram"` — there is no separate refresh credential; the `access_token` column holds the (long-lived, self-refreshing) token directly. `expires_at` is computed from the long-lived exchange's `expires_in` (~5,184,000s / 60 days), same absolute-ISO-timestamp pattern as YouTube/TikTok.

### 2b. Long-lived token refresh needs a proactive periodic job, not a reactive per-publish refresh — CONFIRMED
TikTok refreshes synchronously right before every publish (`refresh-then-persist-then-publish`, `tiktok-publish` Decision 3); YouTube's stable `refresh_token` means every publish already gets a fresh access token via `googleapis`. Instagram has neither: a user might not publish for weeks, and the token would otherwise sit un-refreshed until it's dangerously close to (or past) its 60-day expiry, surfacing as a confusing "reconnect" failure at publish time instead of ahead of it.

**Confirmed:** a new **daily** cron job (own route, not piggybacked onto `credit-expiry` — unrelated domain, and mixing concerns there would make that route's own logic harder to reason about) selects `platform_tokens` rows with `platform = "instagram"` whose `expires_at` falls within the **next 7–14 days**, and calls the refresh endpoint proactively for each. A 7–14 day window (rather than a single fixed cutoff) gives a multi-day safety margin against a single missed/failed cron tick — a row that fails to refresh on day 14-before-expiry still gets ~13 more daily attempts before actually expiring. This job is Phase 3 (not implemented alongside Phase 1's connect/disconnect routes) — see `tasks.md`.

### 3. Publish flow: container → poll → publish, and the poll happens *before* publish, not after
`POST /{ig-user-id}/media` (photo: `image_url` + `media_type=IMAGE`; video/reel: `video_url` + `media_type=REELS`, `caption` = `post.description` either way) returns a `container_id`. **Contrast with TikTok:** TikTok's Init call itself starts the actual publish (upload/pull + async processing) — a returned `publish_id` means TikTok already accepted and is processing the real post, and the status check exists only to catch a failure that's already in flight. Instagram's container, by contrast, publishes **nothing** until `media_publish` is explicitly called — and Meta's API itself refuses `media_publish` unless the container already reports `status_code=FINISHED`. This means Instagram's own API *structurally requires* the status check as a precondition of publishing, not merely as a nice-to-have confirmation step layered on after — exactly the gap `tiktok-photo-post` had to retrofit is built into Instagram's contract from the start.

### 4. Poll model: one status check per cron tick, never an in-request busy-loop
`waitForTikTokPublishOutcome` busy-polls inside a single request (3s interval, bounded at 24s) because it comfortably fits inside the cron's `maxDuration = 60`. Meta's own recommended cadence for Instagram — **once per minute, for up to 5 minutes** — cannot fit that pattern at all: even a single poll at Meta's recommended interval would consume most of the 60s budget, and multiple polls are simply impossible within one invocation. Copying TikTok's busy-loop shape here would be a real bug, not just a stylistic mismatch.

Instead: on each cron tick for an `instagram` post,
1. If `posts.instagram_media_id` is already set → already published (idempotency short-circuit, mirrors `youtube_video_id`/`tiktok_publish_id`).
2. Else if `posts.instagram_container_id` is not yet set → create the container, **persist `instagram_container_id` immediately** (before any status check — same "persist the resumable ID before doing anything riskier" principle as TikTok's `tiktok_publish_id`), then do exactly **one** `GET .../status_code` check this tick.
3. Else (container already exists from a prior tick) → do exactly **one** status check, no container creation.
4. On `FINISHED` → call `media_publish`, store `instagram_media_id`, mark the post `published` (same cleanup calls — `cleanupPostVideo`/`cleanupPostPhotos` — as the existing branches).
5. On `IN_PROGRESS` → release the claim (`publish_started_at = null`), leave `status: "scheduled"` with `instagram_container_id` intact, so the next ~1-minute cron tick re-checks status instead of recreating the container. This is a "pending" outcome, not a retry-count consumer (mirrors TikTok's `outcome: "pending"` handling exactly).
6. On `ERROR` or `EXPIRED` → treat as failure. **Also null out `instagram_container_id`** (unlike TikTok's `FAILED`, which has no equivalent "the ID itself is now dead" wrinkle) so a subsequent retry creates a fresh container rather than re-polling one that can never recover.

### 5. New `posts` columns, additive migration
Mirroring `045_posts_tiktok_fields.sql`'s convention: `instagram_container_id text` (pre-publish idempotency/resume, cleared on `ERROR`/`EXPIRED` per Decision 4) and `instagram_media_id text` (post-publish idempotency, mirrors `youtube_video_id`/`tiktok_publish_id`). Both nullable, meaningful only for `platform = "instagram"` rows, `add column if not exists`.

### 6. Give-up threshold for a stuck/still-processing container is a wall-clock question, not an attempt-count one — CONFIRMED: 10 minutes
TikTok's `MAX_PUBLISH_ATTEMPTS = 3` counts *outright failures* (each a real attempt). Instagram's `IN_PROGRESS` outcome (Decision 4, step 5) isn't a failure at all — at roughly one cron tick per minute, a post could accumulate a very large tick count while still legitimately processing, and `MAX_PUBLISH_ATTEMPTS` as currently defined would either give up far too early (if reused naively as a tick counter) or never fire (if only counting real errors). This needs its own wall-clock-based give-up rule rather than reusing the attempt counter.

**Confirmed:** a post gives up (marked `failed`) if it has been `IN_PROGRESS` for more than **10 minutes wall-clock** since its first Instagram publish attempt, tracked independently of `publish_attempts`/`MAX_PUBLISH_ATTEMPTS`. This is Phase 2 (publish flow) work — not implemented in Phase 1 — but the timestamp this threshold reads from should be decided when Phase 2's migration is written (either a new `instagram_publish_started_at`-style column, or reusing the existing `publish_started_at` claim timestamp from the *first* tick only, since later ticks reset it to `null` on release per Decision 4 step 5). Flagged for Phase 2 implementation, not resolved further here.

### 7. Reuse `signStoragePathForPublish` / `SIGN_TTL.publish` directly — no domain-proxy needed
TikTok's `PULL_FROM_URL` requires a pre-verified domain/prefix registered in the TikTok Developer Portal — `*.supabase.co` isn't ours to verify, which is why `lib/tiktok.ts` proxies photos through this app's own `/api/tiktok-photos/` route (see `tiktok-photo-post/design.md`). Meta's Content Publishing docs describe `image_url`/`video_url` as needing only to be "publicly accessible," with no mention of a pre-registered domain allowlist. Since the media is fetched once at container-creation time — immediately after minting the signed URL in the same request, not re-fetched during the later status polling — the existing `publish`-scoped signed URL (`SIGN_TTL.publish = 900s`, already used by `resolvePublishVideoUrl` for YouTube) is safely reusable as-is for both Instagram photo and video containers. **This is an assumption, not SDK-confirmed** — flagged in Risks below, worth a real smoke test before relying on it broadly (same caveat `connect-tiktok/design.md` raised about TikTok's own undocumented behavior).

### 8. Rate-limit handling: classify, don't pre-check
Given `MAX_POSTS_PER_RUN = 1` keeps overall throughput low, hitting Instagram's 100-posts/24h cap in practice is unlikely — a pre-flight `GET .../content_publishing_limit` call on every single publish attempt would add latency/complexity for a limit rarely approached. Instead, `isInstagramPermanentFailure(err, message)` (mirroring `isTikTokPermanentFailure`/`isPermanentFailure`) classifies Instagram's own rate-limit error response as **transient** (retry later, don't burn the permanent-failure path) alongside the usual auth/scope-failure → permanent, network/5xx → transient split.

### 9. Scheduler UI: Instagram accepts both content types, unlike YouTube
`platforms: Array<"youtube" | "tiktok">` widens to `Array<"youtube" | "tiktok" | "instagram">` (touches `PLATFORM_LABELS`, `PlatformFields`, the `VideoItem`/`BulkVideoCard` types, and every other place this union is spelled out in `app/(app)/tools/scheduler/page.tsx`). Instagram is only offered as a selectable checkbox once `/api/connections/status` reports `instagram: true` (mirrors `tiktok-publish` Decision 7). Unlike YouTube — already disabled for `contentType: "photo"` cards, since YouTube has no photo-post concept — Instagram accepts both a photo (`contentType: "photo"`, single image only per the Non-Goals) and a video/reel (`contentType: "video"`) post, so its checkbox should stay enabled for both card types. **Whether a multi-photo TikTok-style photo card should still offer Instagram (and if so, whether only the cover/first photo publishes, silently dropping the rest) is an open question** — see below; simplest correct behavior is probably to only offer Instagram on a photo card when exactly one photo is staged.

### 10. `media_type` selection mirrors the existing `isPhotoPost` pattern
The cron's Instagram branch decides `IMAGE` vs `REELS` the same way the TikTok branch already decides its own photo/video split: `photo_urls` populated → `IMAGE` (first/only photo — see Decision 9's open question on multi-photo cards); otherwise → `REELS` using the same `resolvePublishVideoUrl`/`publishVideoUrl` the YouTube and TikTok video branches already compute.

### 11. Caption reuse, no new user-facing field
Instagram has a single `caption` field (~2,200 char practical limit). Reuses `post.description` — already the field that maps to TikTok's `description` and (indirectly) YouTube's description — as the Instagram caption. `post.title` stays internal-only, matching the existing pattern where YouTube is the only platform that surfaces `title` externally (as the video title).

### 12. Business/Creator account verification — CONFIRMED requirement, but the originally-assumed mechanism doesn't exist; corrected here
The original ask was to check an `account_type` field on the Instagram user object right after the OAuth callback and reject non-Business/Creator accounts before completing the connection. **Follow-up research for Phase 1 found this field does not exist on the modern API surface used here.** `account_type` (`BUSINESS` / `MEDIA_CREATOR` / `PERSONAL`) was part of the legacy **Instagram Basic Display API**, which fully sunset in September 2025. The **Instagram User** reference for the current "Instagram API with Instagram Login" surface (`graph.instagram.com`) has no `account_type` field at all — Meta's own docs describe the IG User resource as inherently "an Instagram Business Account or an Instagram Creator Account," i.e. the API is defined to only represent Professional accounts, not to classify arbitrary ones. (Sources: [Meta — IG User reference](https://developers.facebook.com/docs/instagram-platform/instagram-graph-api/reference/ig-user), corroborating third-party research cited below.)

Multiple independent sources further indicate Personal accounts **cannot complete Instagram Business Login's OAuth flow at all** — the authorization step itself is gated to Professional accounts, unlike the legacy Facebook-Login-for-Business flow (personal FB login → pick a linked Page/IG account) this app never used. If that holds, most Personal-account attempts should already fail before our `callback` ever receives a `code`.

**Revised, implementable verification mechanism:** the code-for-token exchange response (Decision 2, step 1) already returns a `permissions` string alongside `access_token`/`user_id` — the actual scopes Meta granted, which can differ from what was *requested* if the account/app configuration doesn't support one of them. `callback` parses this `permissions` value and requires `instagram_business_content_publish` to be present before proceeding to the long-lived-token exchange and `platform_tokens` upsert. If it's missing, the connection is **not completed** — no `platform_tokens` row is written — and the user is redirected with a distinct error (`error=instagram_not_business_account`) explaining they need to convert to a Business or Creator account in Instagram's own settings first. This directly satisfies the original intent (don't complete the connection for an ineligible account, show a clear conversion-needed error) using a mechanism that actually exists on this API, rather than a field carried over from the deprecated API by assumption.

This check is **not** purely defensive/theoretical: even if Personal accounts are fully gated at Meta's authorization step (unconfirmed with full certainty — third-party sources, not a Meta doc page directly stating it), a permissions-string check costs nothing extra (the data is already in the token-exchange response) and also catches a subtler, real misconfiguration case — an app or account missing the `instagram_business_content_publish` product/permission setup on Meta's side for reasons other than account type.

### 13. `resolveOrigin` is extracted to a shared location, not duplicated
`lib/tiktok.ts`'s `resolveOrigin(request)` (Host-header + `X-Forwarded-Proto`-based origin resolution, fixing a dev-server/tunnel quirk where `new URL(request.url).origin` reports the wrong address) is provider-agnostic despite living in a TikTok-named file. Per explicit instruction: extract it to `lib/http.ts`, have `lib/tiktok.ts` re-export it (so the existing `import { resolveOrigin } from "@/lib/tiktok"` call sites in `app/api/connections/tiktok/{start,callback}` and `app/api/cron/route.ts` keep working with zero changes), and have `lib/instagram.ts` / `app/api/connections/instagram/{start,callback}` import it from `lib/http.ts` directly rather than from `lib/tiktok.ts`.

## Risks / Trade-offs

- **API specifics not SDK-checked** (no official Instagram Node SDK for either OAuth or Content Publishing) — same caveat `connect-tiktok/design.md` raised for TikTok; recommend a doc diff against Meta's live Developer Portal during implementation.
- **Decision 7's no-proxy assumption is unverified in this codebase** — if Meta's fetcher turns out to have its own quirks (redirect handling, User-Agent blocking, requiring a differently-shaped signed URL), a proxy route mirroring `/api/tiktok-photos/` may still be needed. Worth an early end-to-end smoke test rather than assuming.
- **Reel/video processing time is unbounded within Meta's own 24h `EXPIRED` window** — a large or slow-processing video could stay `IN_PROGRESS` across many cron ticks; Decision 6's give-up threshold is not fully resolved here and needs a product decision.
- **New proactive-refresh infra (Decision 2b)** — this codebase has never needed a "refresh tokens before they're used" job (TikTok/YouTube both refresh reactively at publish time); a missed or broken refresh job silently risks the token expiring between posts, surfacing only as a confusing reconnect error.
- **Instagram Business Login requires an actual Business/Creator account** (not personal) — an external precondition outside this proposal's control, the Instagram equivalent of TikTok's Sandbox/App-Review gate. Decision 12 confirms the app-side check (permissions-string inspection) and error handling, but whether Meta's authorization step actually blocks Personal accounts outright (vs. relying entirely on our own `permissions` check as the real gate) is based on third-party sources, not a Meta doc page directly confirmed during this research pass — worth confirming empirically with a real Personal-account test during Phase 1 implementation.

## Alternatives Considered

- **Busy-poll inside the cron request (TikTok's pattern)** — rejected per Decision 4: Meta's own recommended cadence cannot fit `maxDuration = 60` even once, let alone repeatedly.
- **Reuse TikTok's photo-proxy route (`/api/tiktok-photos/`) for Instagram too** — rejected per Decision 7: no evidence Instagram needs a verified-domain workaround; adds unneeded complexity if the plain signed URL already works.
- **Generic `connections/[platform]` dynamic route** — rejected, same reasoning as `connect-tiktok` Decision 1.
- **Single `instagram_media_ref` column covering both container and final ID** — rejected: pre- and post-publish are semantically different states the resume logic must distinguish (Decision 4's `ERROR`/`EXPIRED` handling specifically needs to null the container ID without touching a hypothetical final-ID column), mirroring why TikTok/YouTube each already have their own dedicated idempotency column rather than a shared one.
- **Attempt-count give-up threshold (reusing `MAX_PUBLISH_ATTEMPTS`)** — rejected per Decision 6: conflates "still legitimately processing" with "failed," which a pure count can't distinguish from tick cadence alone.
- **Checking an `account_type` field to detect Personal accounts** — rejected per Decision 12: this field belongs to the deprecated Instagram Basic Display API and doesn't exist on the "Instagram API with Instagram Login" surface used here; the code-exchange response's `permissions` string is the mechanism that actually exists.
- **Silently restricting a multi-photo card to its first photo for Instagram** — the alternative to Open Question 4's recommendation; not rejected outright since it's still open, but disfavored for the correctness-surprise reason given there.

1. **Env var naming** — **`INSTAGRAM_APP_ID` / `INSTAGRAM_APP_SECRET`**, matching Meta's own dashboard terminology (not `TIKTOK_CLIENT_KEY`-style naming).
2. **Proactive token-refresh job (Decision 2b)** — **new dedicated daily cron route**, refreshing any `platform_tokens` row (`platform = "instagram"`) whose `expires_at` falls within the next **7–14 days**. See Decision 2b. Phase 3.
3. **Give-up threshold for a stuck/still-`IN_PROGRESS` container (Decision 6)** — **10 minutes wall-clock**, tracked independently of `MAX_PUBLISH_ATTEMPTS`. See Decision 6. Phase 2.

6. **`resolveOrigin` reuse** — confirmed: extract to `lib/http.ts`, re-exported from `lib/tiktok.ts` for backward compatibility, imported directly by `lib/instagram.ts`. See Decision 13. Phase 1. ## Open Questions (still need your confirmation)

4. **Multi-photo cards and Instagram (Decision 9)** — since carousels are out of scope, how should a TikTok-style multi-photo bulk card interact with Instagram as a destination? This is Phase 4 (scheduler UI) work, not part of Phase 1, but recorded here since it was raised now. **Recommendation:** disable/hide the Instagram checkbox once a bulk photo card has more than 1 photo staged, rather than silently auto-restricting to the first photo. Reasoning:
   - Silently publishing only the cover photo while the user believes all N photos are going out is a correctness surprise discovered *after* the fact (on the live Instagram account), in the same spirit as the exact class of bug `tiktok-photo-post` had to fix retroactively — this proposal's whole premise is not repeating that pattern.
   - A disabled checkbox (with a short inline note, e.g. "Instagram supports one photo per post — remove extra photos to enable it," mirroring the existing disabled-YouTube-for-photo-cards treatment already in `PlatformFields`) is discoverable at the moment the user is deciding platforms, not after scheduling.
   - It also composes correctly with TikTok being selected on the same multi-photo card (TikTok *does* support carousels) — the two platforms simply have different eligibility for the same card, which a per-checkbox disabled state expresses naturally; a silent-first-photo-only rule would need separate, easy-to-miss messaging to explain why TikTok and Instagram received different content from an identical-looking selection.
   - This flagged for your confirmation before Phase 4 implementation, not decided unilaterally here.

## Phase 2 — Re-Verification & Implementation (2026-07-31)

Decisions 3–8 above were written during Phase 1 as *design*, before any Phase 2 code existed. This section re-verifies them directly against Meta's current docs (per this phase's explicit instruction not to trust Phase 1's design.md blindly — API details can drift, and the OAuth endpoints already drifted twice during Phase 1) and records what Phase 2 actually implemented, including several things Phase 1 did not anticipate.

### Re-verification results

- **Request/response shapes confirmed as designed, with one correction.** `POST /{ig-user-id}/media` (photo: `image_url`+`media_type=IMAGE`; video/reel: `video_url`+`media_type=REELS`) returns `{ "id": "<container_id>" }`; `GET /{container-id}?fields=status_code` returns `{ "status_code": "..." }` (`IN_PROGRESS`/`FINISHED`/`ERROR`/`EXPIRED`/`PUBLISHED`); `POST /{ig-user-id}/media_publish` (`{"creation_id": "..."}`) returns `{ "id": "<media_id>" }`. All three: base URL `graph.instagram.com` (Instagram Login flow, not `graph.facebook.com`/Facebook Login), `Authorization: Bearer <token>` header + JSON body — matching this app's existing TikTok code style, unlike the OAuth endpoints (Decision 12's docs-vs-reality surprises were specific to the *token exchange* endpoints, not Content Publishing). Rate limit re-confirmed directly from Meta's docs: **100 API-published posts per rolling 24h window** (one third-party source claimed 25 during this pass's research — not used; the direct Meta doc citation is trusted over an uncorroborated blog).
- **New, critical finding: JPEG-only, stricter than TikTok.** Meta's docs: "JPEG is the only image format supported... PNG and WebP are not supported." This is *stricter* than TikTok, which accepts JPEG or WebP (`lib/tiktok.ts`'s `ensureTikTokCompatiblePhoto`). Since this app's own generation tools (Product Photo, Storyboard) default to PNG — already the exact reason TikTok needed its own conversion step — Instagram needs the identical treatment from day one, not discovered as a bug later. Implemented as `ensureInstagramCompatibleImage` in `lib/instagram.ts` (own copy of the magic-byte sniff + sharp-JPEG-conversion logic, not a shared import from `lib/tiktok.ts` — see Alternatives Considered below for why).
- **New, critical finding: `platform_user_id` was never persisted — Phase 1 could not have actually published anything.** Instagram's Content Publishing endpoints are scoped under `/{ig-user-id}/...` in the URL itself, unlike TikTok/YouTube (access-token-scoped only). The code-exchange response Phase 1 already receives this ID in (`shortLived.userId`, `app/api/connections/instagram/callback/route.ts`), but Phase 1 only used it for the one-time Business/Creator eligibility check and discarded it afterward — nothing was ever available to build a `/{ig-user-id}/media` URL from. Fixed via `058_platform_tokens_platform_user_id.sql` (new `platform_tokens.platform_user_id` column, generic naming so a future platform can reuse it) and a one-line fix to the callback route to actually persist `shortLived.userId`. **This was a real, shipping-blocking gap in already-"shipped and working in production" Phase 1** — it happened to not matter yet because nothing called the publish endpoints until now.
- **New finding, not yet acted on: Reels video container spec requires "moov atom at the front of the file" (faststart) — this app's Rendi FFmpeg pipeline does not set `-movflags +faststart`.** Grepped `lib/reels-pipeline/*.ts` for `movflags`/`faststart` — no match. This is Instagram-specific: TikTok and YouTube have both worked successfully with this app's existing MP4 output, so this isn't a video-generation bug in general, but Instagram's own docs list the front-moov-atom requirement explicitly as a container spec, and this app's output doesn't currently guarantee it. **Out of scope to fix in this change** (it's the video *generation* pipeline, not the Instagram *publish* integration) but flagged prominently since it could cause real Instagram video/reel publish failures or unusually slow processing that would otherwise look like an unrelated bug. See Risks and `tasks.md`.
- **New finding, not yet acted on: `POST /api/posts` currently rejects an Instagram photo post outright.** `app/api/posts/route.ts` has `if (hasPhotoUrls && platform !== "tiktok") return 400 (...)`, and separately only assigns `insertRow.photo_urls` when `platform === "tiktok"`. This means even a direct API call (not through any UI) cannot create an Instagram photo post today. An Instagram **video/reel** post, by contrast, already passes this route's validation with zero changes (no platform whitelist blocks it). **Not fixed in this change** — this validation lives in the same file Phase 4 (scheduler UI) will need to touch anyway, and the task scoped Phase 4 as out-of-scope for Phase 2. Flagged as a prerequisite: real end-to-end testing of the Instagram *photo* path needs at minimum this one validation line updated, even before any UI work — see `tasks.md`.
- **Signed-URL reusability (Decision 7): no new evidence either way.** Searched specifically for reports of Meta's Content Publishing fetcher rejecting presigned/signed URLs (the same pattern as AWS S3 presigned URLs) — found none, positive or negative. Presigned URLs are an extremely common pattern for exactly this "fetchable without being truly public" use case across many integrations, which is circumstantial confidence, not confirmation specific to Meta's fetcher. **Still an unverified assumption** — the code is written to use it as designed (`signStoragePathForPublish`, reused as-is, no proxy route added), but this is the single most important thing to verify the moment real testing is possible.

### New Decisions (Phase 2)

### 14. JPEG conversion is a standalone copy in `lib/instagram.ts`, not a shared refactor of TikTok's version
`lib/tiktok.ts`'s `ensureTikTokCompatiblePhoto` already does near-identical magic-byte sniffing + sharp conversion. Rather than extracting a shared helper (e.g. `lib/image-format.ts`) and refactoring already-shipped, production TikTok code to use it, Instagram gets its own copy (`ensureInstagramCompatibleImage`). The two aren't quite identical anyway (TikTok accepts JPEG *or* WebP as already-compatible; Instagram accepts JPEG only), and touching stable TikTok code for a DRY improvement carries real regression risk for a small, one-time duplication cost — see Alternatives Considered.

### 15. `platform_user_id` — generic column, fixed at the source
Rather than adding an Instagram-specific column name, `platform_tokens.platform_user_id` is generic (`058_platform_tokens_platform_user_id.sql`), matching the table's existing `platform`-column-driven generic design. Fixed directly in `app/api/connections/instagram/callback/route.ts` (Phase 1 file) rather than working around the gap in Phase 2's cron branch, since the correct fix is capturing the ID at the one point it's actually available (the OAuth callback), not re-deriving it later.

### 16. Instagram photo posts always use `photo_urls[0]` only, regardless of how many are present
Since Instagram is single-image-only (Non-Goals) and Phase 4 (the scheduler UI gate) hasn't shipped yet, the cron branch defensively takes only the first photo even if a post somehow has multiple `photo_urls` targeting Instagram — better to silently publish one correct photo than to error out or attempt something Instagram's `IMAGE` media type doesn't support. This is a backend safety net, not a substitute for Phase 4's planned UI-level restriction (Phase 1 Open Question 4).

## Risks / Trade-offs (Phase 2 additions)

- **Rendi FFmpeg output may not satisfy Instagram's front-moov-atom (faststart) requirement** (see Re-verification above) — not fixed in this change, flagged as a likely source of real publish failures or slow processing specifically on Instagram (not TikTok/YouTube) if left unaddressed.
- **Signed-URL reusability is still unverified against Meta's real fetcher** — no new confirming or disconfirming evidence found this phase either.
- ~~`POST /api/posts` hard-rejects Instagram photo posts~~ — **fixed 2026-07-31** (same day, small isolated change, didn't need to wait for Phase 4): `photo_urls` now accepted for `platform === "instagram"`, capped at exactly 1 photo (no carousel), and actually persisted to `insertRow` (previously only assigned inside the TikTok-only branch).
- **The 10-minute give-up threshold interacts with the "PUBLISHED-without-our-media_publish" edge case** (see `lib/instagram.ts`'s `getContainerStatus` comment): if that ever occurs, the current code treats it as non-terminal (keeps polling) rather than resolving it, and a stuck one would eventually hit the 10-minute give-up and be marked failed even though Instagram itself may have already published it. Low-probability (the crash window is narrow), not specifically handled — flagged for `tasks.md`.

## Alternatives Considered (Phase 2 additions)

- **Shared `lib/image-format.ts` sniff/convert helper for both TikTok and Instagram** — rejected per Decision 14: the two platforms' "already compatible" checks differ (WebP is fine for TikTok, not for Instagram), and refactoring stable production TikTok code for a DRY win wasn't worth the regression risk for ~15 duplicated lines.
- **Deriving the Instagram media type from a new explicit column instead of reusing `isPhotoPost`** — rejected: `photo_urls` presence already unambiguously determines this for TikTok, and the same signal works identically for Instagram; a new column would be redundant.
- **Deferring the `POST /api/posts` Instagram-photo fix to Phase 4** — reconsidered and reversed same-day: the validation fix itself is small and isolated (a platform check + persisting an already-existing field), separable from Phase 4's actual scope (the scheduler UI checkbox/gating). Fixed now since it directly unblocks manual testing once Supabase access returns, without waiting on unrelated UI work.
